# PlanSmart: Security Self-Assessment

FinTechathon 2026 · International Track · Topic A (Personal Finance Assistant)

**Team:** Yang Zhuo, Du Ruiyang, Mo Hanqi, Lin Haoyang · **Date:** 9 October 2026

This report covers two things:

- how PlanSmart limits what its AI agent is allowed to do (the **permission tiers**);
- the security risks we know about, how serious each one is, and what we do or plan to do about it.

Architecture and algorithms are in [TECHNICAL.md](TECHNICAL.md).

## 2. Permission tiers

The core principle: **the AI may look and suggest; only the user may make things happen; money moves
only inside a sandbox, only to the user's own goals and bills, within limits.**

| Tier                         | Who acts                                                                                    | What it can do                                                                                                 | Control                                                                                                                    | Logged                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **0 · Read**                 | Agent, automatically                                                                        | Analyse spending, bills, budgets, goals and the sandbox balance; give recommendations; read a receipt image    | Tools are read-only queries scoped to the signed-in user                                                                   | Yes: every call, with arguments and status (`executed` / `error`)            |
| **1 · Propose**              | Agent proposes, **user confirms**                                                           | Record a transaction; set or remove a budget; save scanned receipt rows                                        | Stored as a pending proposal; nothing changes until the user presses Confirm (or Save after reviewing scanned rows)        | Yes: `pending` → `confirmed` / `rejected` / `expired` / `error`, with result |
| **2 · Direct**               | User, on the app's own forms                                                                | Manual entries, budgets table, savings goals, account settings                                                 | Authenticated, CSRF-protected, validated server-side, ownership-checked                                                    | Yes: tier `user`, with what changed                                          |
| **3 · Move money (sandbox)** | Agent proposes, **user confirms**, plus an **authenticator code** if two-step sign-in is on | Move money from the sandbox account into the user's own savings goals; pay the user's detected recurring bills | Everything in Tier 1, plus allow-listed destinations, 500 per move, 1,000 per 24 hours, atomic balance check, step-up code | Yes: as Tier 1, plus `from`, `to`, `amount`, `balanceBefore`, `balanceAfter` |
| **Not possible**             | Nobody                                                                                      | Real money; paying anyone else; changing or deleting imported transactions                                     | No tool, route or data path exists                                                                                         | n/a                                                                          |

### 2.1 How Tiers 1 and 3 are enforced

Each control below is enforced in code and covered by an automated test.

| #   | Control                                                                                                                                                 | Where                                                   | Test that proves it                                                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Write and move tools only create a proposal; they never write data themselves                                                                           | `writeTool()` in `controllers/finance-agent.js`         | _set_budget only proposes; nothing changes until confirmed_; _transfer_to_goal only proposes; confirming moves the money and logs balances before and after_ |
| 2   | Arguments are checked against a strict schema and business rules before queueing                                                                        | Zod schema + `validate()` per action                    | _rejects unknown categories and invalid limits_; _add_transaction rejects future dates and unknown categories_                                               |
| 3   | At most 5 proposals waiting per user                                                                                                                    | `MAX_PENDING`                                           | _caps the number of pending proposals_                                                                                                                       |
| 4   | Proposals expire after 15 minutes                                                                                                                       | `PENDING_TTL_MS`                                        | _expired proposals cannot be confirmed_                                                                                                                      |
| 5   | Each proposal can be decided once only, as one atomic database operation (no double-execution)                                                          | `decideAction()` uses `findOneAndUpdate` from `pending` | _rejected actions never run, and cannot be decided twice_                                                                                                    |
| 6   | Only the proposal's owner can decide it                                                                                                                 | Query matches `{ _id, user }`                           | _another user cannot confirm someone else's action_                                                                                                          |
| 7   | Arguments are re-validated at the moment of execution                                                                                                   | `decideAction()` parses and validates again             | Covered by tests 1–2 and 10–12                                                                                                                               |
| 8   | Scanned receipt rows are shown for review; each row is validated; the save is all-or-nothing                                                            | `postScan` / `postScanSave`                             | _returns cleaned rows for review and saves nothing_; _saves reviewed rows, all-or-nothing_                                                                   |
| 9   | Every agent tool call is recorded                                                                                                                       | `readTool()` / `writeTool()` → `AgentAction`            | _read tools run immediately and are audit-logged_                                                                                                            |
| 10  | **Money goes only to the user's own goals** (no more than the goal still needs) **or detected bills** (at most 20% above usual)                         | `transfer_to_goal` / `pay_bill` validators              | _refuses unknown goals, more than a goal needs, and amounts over the per-move limit_; _pay_bill pays only detected bills, near their usual amount_           |
| 11  | **500 per move, 1,000 per rolling 24 hours**                                                                                                            | `moveProblem()`                                         | _refuses … amounts over the per-move limit_; _enforces the daily limit across confirmed moves_                                                               |
| 12  | **The balance can never go negative**: debit and balance check are one atomic update; if booking fails, the money is returned                           | `SandboxAccount.debit()`, `moveMoney()`                 | _can never overdraw the sandbox account, even with proposals made while money was there_                                                                     |
| 13  | **Step-up authentication**: with two-step sign-in on, confirming a money move needs a fresh authenticator code; a missing or wrong code changes nothing | `decideAction()` → `User.useTotpCode()`                 | _with two-step sign-in on, confirming a money move needs a fresh code_                                                                                       |
| 14  | **Before and after balances** are recorded for every move                                                                                               | `moveMoney()` result                                    | _transfer_to_goal only proposes; confirming moves the money and logs balances before and after_                                                              |

### 2.2 Why a sandbox, not a real bank

Moving real money has the highest impact and is the hardest to undo. A simulated account lets us show
the complete flow (proposal, limits, confirmation, step-up code, atomic debit, logged before/after
balances) with no financial risk. Connecting a real bank (e.g. through open-banking APIs) would keep
the same tier and controls, and add the provider's own consent and authentication.

## 3. Control checklist

### 3.1 AI-specific risks (OWASP Top 10 for LLM Applications, 2025)

| Risk                                   | Status                    | How PlanSmart handles it                                                                                                                                                                                                                                    |
| -------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LLM01 Prompt injection                 | Mitigated (residual R1)   | Prompts state that transaction text and image text are data, not instructions. Even a successful injection can only read the user's own data or create a proposal the user must confirm. Money can only reach the user's own goals and bills, within limits |
| LLM02 Sensitive information disclosure | Mitigated (residual R4)   | Tools are bound to the signed-in user, so no other user's data can be reached. The agent sees no passwords, card numbers, two-step secrets or other users                                                                                                   |
| LLM05 Improper output handling         | Mitigated                 | AI Markdown is sanitised with DOMPurify before display, behind a nonce-based CSP. Model-supplied search text is regex-escaped. Receipt output must match a typed schema and is then normalised                                                              |
| LLM06 Excessive agency                 | Mitigated                 | Permission tiers above: human confirmation for every change, sandbox-only money movement with allow-listed destinations, limits and step-up authentication                                                                                                  |
| LLM07 System prompt leakage            | Accepted                  | The system prompt contains no secrets; leaking it reveals nothing sensitive                                                                                                                                                                                 |
| LLM09 Misinformation                   | Partly mitigated (R2, R3) | Numbers come from deterministic code, not the model. Prompt rules: "never invent numbers"; not-an-adviser reminder                                                                                                                                          |
| LLM10 Unbounded consumption            | Partly mitigated (R7, R8) | Chat 10/min and scan 10/min per IP; message ≤ 2000 characters; image ≤ about 5 MB; tool loop limit 30; long conversations summarised                                                                                                                        |

LLM03 (supply chain), LLM04 (data and model poisoning) and LLM08 (vector and embedding weaknesses)
mostly don't apply: we use a hosted model with no fine-tuning or vector store. npm dependencies are
covered in R14.

## 5. Compliance considerations

PlanSmart is a prototype, not a regulated financial service. We designed it with these principles in mind:

- **Data protection** (principles shared by the GDPR and China's PIPL):
  - **minimisation:** no card numbers or bank logins;
  - **purpose limitation:** data is used only to answer the user;
  - **right to erasure:** one-click account and data deletion;
  - **transparency:** the operation log.
  - **Gap:** an explicit consent notice for AI processing (R4).
- **Not financial advice:** the assistant analyses the user's own spending and says so; it does not
  recommend financial products.
- **Human oversight of AI:** every change and every money movement proposed by the AI needs explicit
  approval (with step-up authentication for money when two-step sign-in is on), and every AI action is
  recorded.
- **Payment services:** PlanSmart moves only simulated money in a sandbox and connects to no bank or
  payment provider. A real-money version would need a licensed partner (e.g. an open-banking provider)
  and strong customer authentication; the move tier and step-up code are designed for that.
